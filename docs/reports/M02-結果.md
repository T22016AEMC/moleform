## 3. R5：改寫後重建分子

### TS 在改什麼、為什麼

`stripSubstituents` 只在「書中基團配不到（缺基團）且有『H 換成 X』增量（目前只有酚羥基 `CAL.OH.ar`）」時才走到。它要把芳香環上的 –OH 換回氫（Table 6.20 的做法），再用書中基團切分。步驟：

1. `mol.get_json()` 取 JSON（原子順序＝RDKit 原子索引；原子只記與預設不同的 `z`、`impHs`＝總氫數、`chg`、`nRad`、`isotope`、手性 `stereo`；鍵記 `bo`——芳香環寫成 Kekulé 單／雙鍵——、雙鍵 `stereo` 與 `stereoAtoms`；芳香性另放 `extensions`）。
2. 刪掉被移除的原子與連到它們的鍵，其餘原子保持原順序重新編號，原本連到被移除原子的原子 `impHs` 加上被移除的鍵數。
3. `delete m.extensions`：丟掉芳香性資訊，讓 RDKit 重新判定。
4. `get_mol(JSON)` 重建並 `get_smiles()`；重建失敗（null）→ 回傳 null，呼叫端退回書中基團的缺基團結果。之後第二次切分是以這個 canonical SMILES 重新解析，所以最終輸出的原子索引取決於 canonical SMILES 的原子順序。

### Python 做法與依據

分兩步，對應 TS 的「改寫 JSON」與「`get_mol(JSON)`」，**沒有任何字串處理**（canonical SMILES 一律由 `Chem.MolToSmiles` 直接取得）：

- `rewrite_without_atoms`：從 RDKit 物件讀出同一組欄位（Kekulé 化的複本）、刪原子、重新編號、補氫，得到與 TS 改寫後 JSON 的 atoms／bonds 同形的資料。
- `rebuild_molecule`：用 `RWMol` 逐一 `AddAtom`（`NoImplicit` 加明確氫數、電荷、同位素、自由基、手性）、依序 `AddBond`，**最後才**設雙鍵順反與 `stereoAtoms`，再 `SanitizeMol`（對應「沒有 extensions → 重新判定芳香性」）。
- 依據：不是憑推測，而是用匯出時攔截到的 TS 實際輸入／輸出逐項比對（見下）。先用 78 個分子在 Node 與 Python 之間做過原型比對，再固化成黃金案例。

> **與任務卡前提不同的一點**：Python 的 RDKit 其實有 JSON 輸入路徑（`rdMolInterchange.JSONToMols`）。我仍照任務指示用 `RWMol`；另外確認過直接走 JSON 路徑在 16 個候選案例上要多加 `AssignStereochemistry(cleanIt=True, force=True)` 才與 TS 一致（RDKit.js 與 Python 的 JSON 載入預設不同），`RWMol` 路徑不需要額外步驟就一致，所以維持 `RWMol`。

### 結論：canonical SMILES 與重建後原子順序與 TS 逐字一致

- 專屬案例 121 個（`R5/…`，117 個走到改寫、4 個對照案例不走；列出 123 筆，2 筆因 SMILES 與先前案例重複被去重）：含 `*`（連接點 14）、雜環（17）、稠環（12）、雙酚茀（3）、手性（17）、雙鍵立體（20）、帶電／同位素／自由基／明確氫／其他取代基（28）、少見的鍵與原子（配位鍵、硫／磷／矽的四面體手性、橋環、累積雙鍵、金屬離子、環庚三烯酮，8）。加上其他來源，r5 共 140 案、重建 136 次。
- 比對內容：改寫後的原子（z、氫數、電荷、同位素、手性）與鍵（原子對、鍵級、順反、`stereoAtoms`）逐項、canonical SMILES 逐字、重建是否成功、最終輸出。**全部一致，沒有需要停下來回報的差異。**
- 反向驗證（確認案例有鑑別力）：不 Kekulé 化 136 個失敗；不補回氫 184；不 sanitize 132；保留原子映射 91；丟掉手性 23；丟掉電荷 8；丟掉同位素 4；重新編號 `stereoAtoms`（修掉 TS 的特性）4。

### TS 這段的已知特性（Python 照做，不修正；TS 不改）

1. **原子映射編號消失**：`[*:1]` 重建後是 `*`（JSON 沒有映射編號）。
2. **雙鍵順反標示在 canonical SMILES 裡一律消失**（17 個帶順反標示的重建，canonical SMILES 都不含 `/`、`\`）。後果：酚羥基單元若含 `–CH=CH–`，第二次切分取不到 cis／trans → 回報缺基團（單元測試 `test_r5_known_ts_behaviours_are_reproduced`）。
3. **`stereoAtoms` 沒有重新編號**（只重編鍵的 `atoms`）：被移除原子的索引小於順反標示所指原子時，重建失敗（RDKit.js 回 null、Python 同樣拋例外 → None），結果退回缺基團。4 個黃金案例是這種情形。理論上索引恰好仍是鄰居時會靜默標錯順反，目前案例沒有碰到。
4. **空字串**：RDKit.js 的 `get_mol('')` 得到沒有原子的有效分子，之後 `get_json()` 拋 WebAssembly 例外，`computeTg` 沒有接，直接拋出。黃金檔記為 `{ threw: true }`，Python 同樣拋 `EmptyMoleculeError`；HTTP 介面先擋下空白輸入回 400。

## 9. 需要使用者決定的事

1. **引擎回應的 `status`**：算得出的 Tg 標 `"predicted"`（沿用 M01）；含校準基團時另有 `containsCalibrated: true`。若要標 `"literature"`，只需改 `handle_tg` 一行。
2. **資料表格式錯誤**：TS 的 `YG_GROUPS` 會靜默丟掉格式錯誤的列；Python 載入時直接拋 `TgDataError`（D22；沿用 M01 第 8 節的決定，記為已知差異，不改 TS）。
3. **資料表路徑**：沿用 M01 的 `DATA_DIR`（預設專案根目錄 `src/data`，環境變數 `MOLEFORM_DATA_DIR` 可覆寫）。D63 內嵌打包時再決定。
4. **TS 的 R5 特性（第 3 節 2、3）**：酚羥基單元若含有標示順反的 `–CH=CH–`，TS（與 Python）會因順反資訊在改寫時遺失而回報缺基團；其中一部分情形是 `stereoAtoms` 沒重新編號造成的失敗。這屬於 TS 計算的問題，本卡依規定沒有改。要不要之後在 TS 與 Python 同步修正（例如重編 `stereoAtoms` 或改為不經 canonical 化），請決定。
5. **空字串**：TS 的 `computeTg('')` 拋出例外而非回傳 `invalid`（第 3 節 4）。是否要在 TS 端補成 `invalid`，請決定（目前 Python 與 TS 一致地拋出）。
6. **`scripts/golden/*.ts` 不在 `tsconfig.json` 範圍**（M00 已提）：`export-tg.ts` 同樣沒有型別檢查（實際執行過，產出正常）。
7. **黃金檔重產規則**：`tg.json` 會隨 `src/data/yg_*.csv`、`tgGroupContribution.ts`、`ygGroups.ts`、`ygCalibratedGroups.ts`、`bookCases.ts`、`backbone_templates.csv`、`tg.test.ts`／`ygCalibrated.test.ts` 內的 SMILES 字串、`docs/verification` 的 Tg 輸出與 `scripts/verification` 的分子清單改動而變，`golden-fresh` 會抓到並要求重產。
