# 報告 005：測試 OpenChemLib JS 的 3D 能力

日期：2026-10-29

## 結論（先講）

`openchemlib` 9.25.2 在 Node 環境**支援** MoleForm 需要的 3D：產生 3D 座標、MMFF94 最佳化、多構象與能量、輸出含 3D 座標的 MOL／SDF。RDKit.js 輸出的 molblock 交給它之後，**原子順序不變**（重原子在前、氫在後），所以 Phase 4 在 3D 上標記 RDKit 找到的反應原子可行。主要缺點：MMFF 力場沒有退路、較大分子耗時數秒、**瀏覽器端實測與 3D 顯示函式庫尚未驗證**。P01 依你的指示不決定，下面只比較選項。

## 測試結果（逐項，3 個分子：乙醇、環氧丙烷、BADGE）

| # | 檢查項目 | 結果 | API／說明 |
|---|---|---|---|
| 1 | 3D 座標（z 不全為 0） | **支援** | `new ConformerGenerator(seed).getOneConformerAsMolecule(mol)`；會自動補上明確氫原子（乙醇 3→9 個原子、環氧丙烷 4→10、BADGE 25→49）。z 範圍：乙醇 [-3.51, -0.03]、環氧丙烷 [-2.69, 0.38]、BADGE [-5.88, 4.84]（皆不全相同）。`Molecule.is3D()` 可確認 |
| 2 | MMFF94／MMFF94s 最佳化；缺參數的退路 | **支援；沒有退路** | `new ForceFieldMMFF94(molecule, 'MMFF94'｜'MMFF94s'｜'MMFF94s+')` → `getTotalEnergy()`、`minimise()`（回傳 0 為成功）。三個表格三個分子皆成功。型別定義中**沒有 UFF 或其他力場**。缺參數時直接拋錯：`CB(C)C`（硼）與 `FS(F)(F)(F)(F)F`（硫，SF6）出現 `Couldn't assign an atom type to atom …`；矽（四甲基矽）與磷（三甲基膦）則成功。因此 MoleForm 需自行處理：捕捉錯誤，改為只顯示未最佳化的初始構象並標示 |
| 3 | 多構象與每個構象的能量 | **支援（能量需自己組合）** | `initializeConformers(mol, {strategy, maxTorsionSets, use60degreeSteps})`、`getNextConformerAsMolecule()`、`getConformerCount()`、`getPotentialConformerCount()`、`molecules()`。BADGE 得到 30 個構象（上限我設為 30；潛在構象數 20,736，可旋轉鍵 8）。能量要對每個構象另建 `ForceFieldMMFF94` 並 `minimise()` 後取 `getTotalEnergy()`。BADGE 相對能量範圍 0–6.3；其中有些構象最佳化後能量相同（可能收斂到同一構型，**未去重**）。乙醇與環氧丙烷各只得到 1 個構象：OpenChemLib 不把羥基氫的轉動當作可旋轉鍵（乙醇 `getRotatableBondCount()` 為 0）。**能量單位型別定義沒有註明**，本報告不下結論 |
| 4 | 輸出含 3D 座標的 MOL 與 SDF | **支援** | `Molecule.toMolfile()`（V2000）、`toMolfileV3()`；SDF 為 molfile 加 `$$$$` 自行組成（腳本也寫入 MMFF 能量欄位）；讀 SDF 有 `SDFileParser`。三個分子的 MOL／SDF 都在 `output/`，重新讀回 `fromMolfile` 後 z 範圍仍不為 0 |
| 5 | 鍵長、鍵角、二面角 | **部分支援，有一個陷阱** | `calculateTorsion(atoms[4])` 回傳弧度，可用於 3D。**`getBondLength(bond)` 依型別定義註解是由 2D 座標計算**（`getBondAngle(atom1, atom2)` 型別定義無說明，疑為 2D 鍵方向角，未測，不要用）：實測 `getBondLength` 在 3D 分子上與座標算出的真實鍵長不一致（乙醇 0.376 vs 1.506 Å）。因此**鍵長與鍵角必須自行由 x、y、z 計算**（腳本已示範，鍵角約 109–111°，合理）。座標由 `getAtomX／Y／Z` 或 `getCoordinates(atom)` 取得 |
| 6 | 每項記錄支援與否及 API | 如上表 | 完整輸出在 `output/results.json` |
| 7 | 與 RDKit.js 的原子編號對應 | **一致（本次測試範圍內）** | 見下節 |
| 8 | 3D 顯示 | **OpenChemLib 沒有 3D 顯示元件** | 型別定義內只有 2D 的 `CanvasEditor` 與 `<openchemlib-editor>` 元素，沒有 3D 檢視器。顯示需另配函式庫，見下節 |

### 第 7 項：與 RDKit.js 的原子編號對應

做法：RDKit.js 先 `get_mol(smiles)`，產生 2D 座標，分別取「不加氫」與「`add_hs()` 加氫」兩種 molblock，用 `Molecule.fromMolfileWithAtomMap()` 解析，再交給 `ConformerGenerator.getOneConformerAsMolecule()` 產生 3D。

結果（三個分子都相同）：
- **解析後原子順序與 RDKit 相同**（元素順序逐一比對；`fromMolfileWithAtomMap` 回傳的 map 為 0,1,2,…，即恆等對應）。
- **產生 3D 後，重原子保留原索引（前 N 個），新加入的氫接在重原子之後**（乙醇重原子 0–2、氫從索引 3 開始；環氧丙烷氫從 4；BADGE 氫從 25）。
- 若 RDKit 已先加氫再交給 OpenChemLib，氫的順序也保持與 RDKit 相同，原子數不變。
- 重原子之間的鍵，以索引比對，與 RDKit 完全一致。

所以做法可以是：**RDKit 的原子索引 i（重原子）= OpenChemLib 3D 分子的原子索引 i**，不需要另外建對照表。注意：
- 這個結論只對「用 RDKit molblock 當輸入」成立。若直接用 `Molecule.fromSmiles()`，OpenChemLib 可能用自己的順序，這次**沒有測**，不要這樣做。
- 只測了三個分子，沒有測含立體中心、芳香環不同 Kekulé 形式、或金屬的分子；建議正式實作時加自動測試。

- BADGE 的構象產生與最佳化在 Node 中就需數秒到十數秒；若要在瀏覽器即時顯示，需要放進 Web Worker 並限制構象數。

## 對架構的建議（由使用者決定，P01）

背景事實：RDKit.js 不能做 3D（任務 001）；`openchemlib` 在 Node 測試中可以。**尚未測的部分**：瀏覽器中的實際效能（尤其 BADGE 等較大分子）、`resources.json` 的載入、3D 顯示函式庫整合、化學品質（構象與 MMFF 能量是否合理，依 D17 由使用者驗證）。

| 選項 | 內容 | 優點 | 缺點／風險 |
|---|---|---|---|
| A. 純前端，3D 降級 | 只做 2D，不做 3D 顯示與量測 | 最簡單；無新增套件；不用處理效能與 3D 顯示 | 失去 spec 的 3D 功能；反應位點「3D 空間位阻」排序只能降級 |
| D. 純前端：RDKit.js 管 2D／SMARTS／描述子，OpenChemLib 管 3D | 兩個 BSD-3-Clause 函式庫並存；RDKit 的 molblock 交給 OpenChemLib，索引一致 | 不需伺服器，符合 D23、D24；3D 全功能（構象、MMFF94、能量、MOL／SDF）；原子對應已驗證；多裝約 2.4 MB（js＋resources），遠小於 RDKit WASM | 兩套化學函式庫要維護；MMFF 無退路（部分元素會失敗，需降級顯示）；較大分子耗時數秒（需 Web Worker）；鍵長、鍵角要自行計算；3D 顯示函式庫仍需另選；化學品質未驗證；兩個函式庫對結構的詮釋可能有細微差異（立體、芳香）需測試 |
| C. 3D 另用 Python 服務 | 後端用 Python RDKit 做 ETKDG、MMFF94／UFF | 功能最完整；有 UFF 退路；計算不佔使用者瀏覽器 | 需要伺服器與部署維護，直接牽動 D23（不使用伺服器）與 D24（靜態網站）；要設計 API |

我的建議（僅供參考）：D 值得先做一個更小的驗證（瀏覽器內實測 BADGE 與一個含雜原子分子，並串 3Dmol.js 顯示），結果可接受就採用 D；若瀏覽器效能或化學品質不行，退到 A，C 是最重的備案。**由你決定。**
