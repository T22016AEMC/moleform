## 3. 風險 R1、R3、R4

### R1 芳香性

**做法**：芳香旗標用 `atom.GetIsAromatic()`（M00 的 `read_graph`），對照 TS 的 `aromaticAtoms`。VW 中依賴芳香性的地方有三處：SMARTS 的 `c`／`[c;R2…]`、`describeAtom` 的「（芳香）」、`dummyEndClass`（連接點另一端接芳香還是烷基，決定 BG12／BG13）。
**專屬案例**（`R1/…`，59 個 compute）：雜環（吡啶 2／3／4 位、吡咯、呋喃、噻吩、咪唑、嘧啶、吡啶鎓）、Kekulé 寫法（苯、甲苯、吡啶）、無法 kekulize 的 `c1cccc1`、稠環（萘各取代位置、蒽、菲、芘、薁、吲哚、喹啉、咔唑、茀、9,9-二甲基茀、茚滿、四氫萘）、含 `*` 的單元（伸苯基、呋喃、噻吩、吡啶、萘 2,6、咔唑、PET、PEEK、PMDA–ODA、`*` 位在芳香環內的 `c1cc*cc1`）、連接點另一端的芳香／烷基／雜原子／三個連接點／單一連接點。
**結論**：全部一致，包含 BG12（芳香端）與 BG13（烷基端）分別配對到預期的基團。
**反向驗證**（確認案例有鑑別力）：把芳香旗標全清掉，37 個 compute 案例失敗。

### R3 SMARTS 配對順序

**TS 端實際行為**：`mol.get_substruct_matches(query)`（RDKit.js，不帶 details，即預設參數）→ 每個命中的原子由小到大排序 → 命中之間依序比較排序（`vwMatches`）。這兩個排序是 TS 演算法本身，Python 照搬（`vw_matches`）；不是為了遮蓋差異而加的。
**Python 端**：`GetSubstructMatches(query, SUBSTRUCT_PARAMS)`，參數明確列出：`uniquify=True`、`useChirality=False`、`useEnhancedStereo=False`、`useQueryQueryMatches=False`、`recursionPossible=True`、`aromaticMatchesConjugated=False`、`maxMatches=1000`、`numThreads=1`。
**確認方式**（兩層）：
1. **原始順序逐字比對**：350 個分子 × 61 個 SMARTS，比對 RDKit.js 與 Python 的**未排序**命中順序，以及每個命中內的原子順序。全部相同，所以兩邊在排序之前就一致，不是靠排序對齊。
2. **參數探針**（21 個）：`uniquify`（苯對苯環 1 個命中、萘 2 個環、聯苯 2 個）、`useChirality`（相反手性仍命中）、遞迴 SMARTS、命中內原子順序＝查詢原子順序、對稱酯基、環旗標、500 個命中、啞原子 `[#0]`。反向驗證：`uniquify=False` 讓 6 個探針失敗，`useChirality=True` 讓 1 個失敗，`maxMatches=3` 讓 4 個失敗。
**專屬案例**（`R3/…`，36 個 compute）：PMMA／PEMA／PVAc／PMA 單元、PGMEA、酯 vs 醚、酸酐、草酸酯、碳酸酯（含 BPA 單元、二芳基碳酸酯）、醯胺 vs 三級胺、尼龍 6,6、鄰／間／對位苯二甲酸酯、二甲基／二苯基伸苯基、萘基 1／2／2,6／2,7、環己基、異丙基、新戊烷、BPA、BADGE、茀雙酚、SBI、PDMS 單元等。
**切分確實取決於配對順序**（所以這項檢查不是形式）：把命中順序反過來，4 個案例的切分結果改變（酸酐 `R3/anhydride`、V42 的一個反例、031 驗證的兩個分子）；完全不排序則 66 個改變。這些在 Python 與 TS 都相同。
**結論**：一致。
**限制（已確認、未能涵蓋）**：RDKit.js 解析 900 個以上原子的鏈會直接判為無效（700 個還可以），所以 `maxMatches = 1000` 的上限在 RDKit.js 這一側無法用黃金案例觸發。Python 明確設為 1000（與 RDKit 預設相同）。VW 的單一 SMARTS 命中數最多約等於原子數，實務輸入碰不到。`aromaticMatchesConjugated` 的探針在兩種設定下結果相同（沒有鑑別力），資料表的芳香原子都用 `c`，不依賴此參數。

### R4 SMARTS 解析

**做法**：`Chem.MolFromSmarts`（對應 `RDKit.get_qmol`），無法解析時與 TS 一樣拋出 `VW 基團表的 SMARTS 無法解析：…`。
**測試**：資料表 61 列（書 43、Bondi 13 基團＋5 修正）**每一列**在 Python 都能解析；測試用的 SMARTS 取自 Python 實際載入的 CSV，且必須與黃金檔記錄的相同（資料表改了就失敗，提醒重產黃金檔）。正例／反例配對（`vwMatches`，已排序）與 TS 逐字相同。另有 7 個無法解析的 SMARTS（括號不成對、未知元素、遞迴未關閉、環未關閉、非 SMARTS 文字等），兩邊都判為無法解析。
**結論**：一致。

### 其他一致性（R2 相關，一併確認）

原子索引、氫數、基團順序與 TS **全部一致，沒有需要停下來回報的差異**。反向驗證：改用 `GetNumImplicitHs()` 讓 12 個案例失敗。

## 4. 本卡才發現的陷阱（給之後的搬遷卡）

- **Python 3.12 的內建 `sum()` 對 float 使用補償加總**，與 JS `reduce` 的由左至右逐項相加不同。把 VW 的三處加總（VW、ΣMi、修正量）改成 `sum()`，39 個 compute 案例的 `massDelta` 等欄位會差約 1e-12 以上而失敗。`vw.py` 一律用明確迴圈。之後搬遷其他物性模組都要沿用。
- JS 的 `Math.round`（.5 往正無限大）與 Python `round`（銀行家捨入）不同，`vw.py` 另寫 `_js_round`。目前黃金案例沒有碰到 .5 的邊界（改用 `round` 仍全數通過），所以這一條沒有案例佐證，只是依規格忠實移植。

## 8. 需要使用者決定的事

1. **引擎回應的 `status`**：算得出的 VW 我標為 `"predicted"`（基團增量估算，非實測）。若要標 `"literature"`（資料表來自書／Bondi 論文），只需改 `handle_vw` 一行。
2. **資料表格式錯誤時的行為**：TS 的 `VW_GROUPS` 會靜默丟掉格式錯誤的列（靠測試把關）；Python 端載入時只要有任何格式問題就直接拋出 `VwDataError`（D22 精神，不靜默略過）。資料正常時兩者結果相同。是否同意？
3. **資料表路徑**：`vw.py` 預設讀專案根目錄的 `src/data`（可用環境變數 `MOLEFORM_DATA_DIR` 覆寫）。D63 內嵌打包時需要決定資料表如何隨引擎發行，同時維持單一來源。
4. **`scripts/golden/*.ts` 不在 `tsconfig.json` 範圍**（M00 已提）：`export-vw.ts` 同樣沒有型別檢查（實際執行過，產出正常）。
5. **黃金檔重產規則**：`vw.json` 會隨 `src/data/vw_groups*.csv`、`vanDerWaalsVolume.ts`、`vwCases.ts`、`vwBondiCases.ts`、`backbone_templates.csv`、`docs/verification` 的分子清單改動而變，`golden-fresh` 會抓到並要求重產。
