## 2. 框架

- **匯出**（`scripts/golden/`）：`common.ts` 負責共用輸出格式，另有 `export-atomicWeights.ts`、`export-csv.ts`、`export-molGraph.ts`。用 `node scripts/golden/export-<module>.ts` 執行，做法與 `scripts/verification` 相同（Vite `ssrLoadModule`），只呼叫現有函式。輸出 `tests/golden/<module>.json`，格式為 `{ module, commit, rdkitjs, cases:[{id,input,output}], tolerance }`。鍵排序後才序列化；Map 寫成 `{"$map":[[k,v],…]}`，保留原本順序；非有限數字明確標示；遇到 `undefined` 直接丟錯。
- **比對**（`engine/tests/golden_compare.py`，加上 `conftest.py` 與 `test_golden_*.py`）：
  - 字串、整數、布林、null、陣列、物件鍵：必須完全相同。
  - 浮點：先比最短 round-trip 字串。JS 數字字串的規則已用 Node 24 實測核對。字串不同時，只有 Python 端是 float 才接受相對誤差 ≤ 1e-12，並把案例記入 `tolerance_cases`；整數一律不放寬。
  - 黃金檔裡的 `relFallback` 只要不是 1e-12，比對程式就拒絕讀取。
  - **版本不符時拒絕比對**：黃金檔的 `rdkitjs` 與引擎握手（`handshake_payload`）回報的版本不同，或引擎沒有 RDKit，就判為測試失敗（不是略過）。
  - `tolerance_cases` 寫到 `engine/.reports/tolerance_cases.json`（已加入 gitignore），也會列在 pytest 的終端摘要。
- 框架本身另有測試（`test_golden_framework.py`）：版本不符要拒絕、數字字串規則、放寬後必須有記錄、整數不放寬、Map 順序。

## 3. 共用層三塊（`engine/moleform_core/`）

| 模組 | 做法 | 黃金案例 |
|---|---|---|
| `atomic_weights.py` | 數值逐字取自 `src/core/properties/atomicWeights.ts`；黃金案例包含整張表，兩邊表不同就會失敗 | 125（整張表；z = −1…120；非整數） |
| `csv_reader.py` | 逐行移植 `parseCsv`、`splitList`、`readTable`（標題列、欄位數、數字、整數清單，D22）。另外實作 JS 的 `trim` 與 `Number()`，因為 Python 的 `strip`／`float`／`\d`／`$` 規則不同（例如 `1_000`、`inf`、全形數字） | 157（`csv.test.ts` 的輸入、邊界情況、`src/data/*.csv` 全部 21 個檔、四個讀取器的錯誤情況；TableDef 放在 input 裡，Python 不另外抄一份） |
| `mol_graph.py` | `Chem.MolFromSmiles`（對應 `RDKit.get_mol(smiles)`，不帶選項）→ 依原子索引直接讀 | 495（R1 專屬 41、R2 專屬 33；另有 421 個 SMILES 取自 `tests/**/*.test.ts` 與 `docs/verification/*.md`） |

**R1 芳香性**：用 `atom.GetIsAromatic()` 對應 JSON 的 `extensions[rdkitRepresentation].aromaticAtoms`。
- 結論：495 例全部一致。其中 246 例含芳香原子、253 例含 `*`。
- 涵蓋：雜環（吡咯、呋喃、噻吩、吡啶、咪唑、嘌呤等）、稠環（萘、蒽、芘、薁、吲哚、咔唑、茀等）、含 `*` 的單元（芳香端、烷基端、`*` 位在芳香環內的 `c1cc*cc1`，兩邊都把 `*` 判為芳香）。
- 無法 kekulize 的 `c1cccc1`：兩邊都判為無效。

**R2 隱式氫與原子順序**：
- 用 `atom.GetTotalNumHs()` 對應 JSON 的 `impHs`。原子順序直接用 RDKit 原子索引，也就是 SMILES 的解析順序，**沒有做任何排序或重排**。鄰居清單的由小到大排序是 TypeScript 原本就有的步驟，照搬。
- 結論：495 例的原子順序、氫數、鄰居全部一致。
- `[H]` 明確氫兩邊都併入重原子的氫數；`[2H]` 兩邊都保留為原子（z=1）。
- 順反：RDKit 寫 JSON 時把 Z 寫成 cis、E 寫成 trans，Python 用 `bond.GetStereo()` 做同樣的對應。11 例含順反，全部一致（包括依 CIP 判定的 `C/C=C(/F)Cl`）。
- **反向驗證**（確認比對不是太寬鬆）：故意做錯的版本都會被抓到。改用 `GetNumImplicitHs()` → 29 例失敗；改用 canonical 原子順序 → 456 例失敗；清除芳香旗標 → 246 例失敗。

## 7. 需要使用者決定的事

1. **CI 的 Python job**：是否照第 6 節加入。
2. **`npm run engine:test`**：目前用 unittest，只會跑 `test_engine.py`，黃金比對要用 pytest 才會執行。本卡規定 `package.json` 只能改 RDKit 那一行，所以沒有改。是否改成 `python -m pytest engine/tests`？
3. **requirements 是否加 hash**（039a 的建議）：本卡依任務只用 `==`。建議在內嵌打包（D63）時改用 `pip-compile --generate-hashes` 或 `pip install --require-hashes`。
4. **黃金檔重產規則**：`tests/golden/csv.json` 內含 `src/data/*.csv` 的全文。資料表或 TS 計算有任何改動，都要重跑 `scripts/golden/export-*.ts`；黃金檔的 `commit` 欄位會記錄產生時的 HEAD，src 有未提交的改動時會加上 `+dirty-src`。
5. `scripts/golden/*.ts` 與 `scripts/verification` 一樣不在 `tsconfig.json` 的 include 範圍內，型別檢查不會涵蓋這些檔（本卡實際執行過，三個都正常產出）。是否要納入型別檢查？
